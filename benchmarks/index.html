MVCC store benchmarks: Python and Rust

The same multi-version concurrency control (MVCC) store exists twice in ExplainDB: in Python, as used by the course notebooks, and as a port to Rust with the same algorithm. On the machine below, Rust is between 15× and 75× as fast as Python.

What is measured

Seven workloads run on both stores with the same data: a store of n objects, each with two numbers a and b computed from its position. Only the work in the list below is timed; building the data, and filling the store for all workloads but bulkload, are not.

  • bulkload: loading n objects, time per object.
  • get: one non-transactional get of every object, time per get.
  • read: 100 reads of the objects with a == 42 in one transaction, time per read; each read scans all n objects.
  • update_commit: 1 000 transactions of one update and a commit, time per transaction.
  • read_only: 1 000 transactions reading the objects with a < 100, time per transaction.
  • read_write_disjoint: 1 000 transactions each reading one object and updating it, without conflicts, time per transaction.
  • read_write_contention: 500 pairs of transactions on the same objects where the second fails validation, time per transaction, committed or aborted.

The first four, the micro-benchmarks, run with 100, 1 000 and 10 000 objects and validation method 2; the last three with 1 000 objects and both validation methods: method 1 compares checksums of everything a transaction read, method 2 checks which objects concurrent transactions wrote.

Each benchmark (workload, store size and validation method) runs in its own process, once per language. A pass runs the workload on a fresh store; a repetition repeats passes until their timed parts add up to at least 50 ms. After a warm-up, 7 repetitions are measured; the charts show their median, the micro-benchmark charts also their range as thin bars, and the table shows every range. Python's garbage collector is switched off during a repetition, as Python's timeit does. After every pass both programs report a fingerprint of the work done (commits, aborts, objects read, the final transaction counter, which counts begins and commits, versions stored and a checksum of the final objects), and the run stops if Python and Rust differ.

How fair is the comparison?

Both stores run the same algorithm on the same data, single-threaded, and both scan all objects for every read_objects and keep every version, so both pay for the algorithm itself. The comparison measures the two implementations, not the languages alone: Python also pays for its pydantic version and journal objects, for deep copies on writes and for the generator of get; Rust pays for copies of the objects and ids it returns from read_objects and of the values it puts into the journal on updates. How to reproduce

In a checkout of the ExplainDB repository with Python (uv) and Rust installed, on an otherwise idle machine on mains power:

uv run python -m system.benchmarks.run
uv run python -m system.benchmarks.report

The first command measures and writes benchmarks/results.json; the second writes this page.

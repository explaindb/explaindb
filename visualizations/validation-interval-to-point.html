From a Time Interval to a Point in Time

Every transaction runs from its begin timestamp to its commit timestamp. Under the isolation level serializable, a transaction that commits may be treated as if it ran entirely within a single moment: the interval becomes a point.

Why is this allowed?

A transaction T reads its snapshot as of begin. Its writes become visible only at commit. Validation looks at all transactions that committed after the begin and before the commit of T and combines their write sets. If nothing that T read is in that set, T would have read exactly the same at its commit timestamp as at begin. (Here every read fetches single objects. In the store, a read is a WHERE clause, so an object written in the meantime that now matches one of the reads of T counts as well.) This is the default validation method of the store; the other one (brute force) instead runs every read of T again at its commit timestamp and compares the results, which gives the same verdicts in this example.

So T behaves as if it had performed all its reads and writes in a single moment: at commit. If validation fails, the commit does not work as the moment of T; validation does not look for another one, so T is aborted.

Read-only transactions (R1, R2) are not validated. They read the snapshot as of begin and write nothing, so begin is their moment. At commit, their view might already be outdated. As MVCC keeps the old versions they read and validation checks only writing transactions, they never have to abort in this store.

Lining up all points gives an equivalent serial schedule. begin and commit draw their timestamps from the same counter, as in TransactionalKeyValueStore; the transaction id is the begin timestamp.

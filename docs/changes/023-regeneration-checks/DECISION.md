# 023 — Checks for a regeneration of the Rust code
**Date:** 2026-10
**MR:** https://gitlab.cs.uni-saarland.de/bigdata/dbsys/explaindb/-/merge_requests/166
---
## Context

The Rust code in `generated/rust/` is generated by an AI from the Python code in `system/`, and the CI builds and
tests it. A short skill `/regenerate-rust` is to drive the regeneration; like a build system, the tools do the
mechanical steps (see [021's DECISION.md](../021-generated-source-snapshots/DECISION.md)). Two things a regeneration
must not do were not enforced by a tool: change the Cargo files (dependencies, toolchain, build settings), and bring in
code that reaches the system (processes, network, files, environment) or the build (build scripts, included files).
`unsafe_code = "forbid"` in `Cargo.toml`, the hand-edit detection of the check and the review already cover part of it.

## Decision

- `--update` refuses while a Cargo file (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`) differs from the
  manifest (changed, added or deleted), before it writes copies or the manifest: a regeneration keeps the Cargo files,
  and a change of them is a human decision recorded with `--update-dependencies` (which now covers every Cargo change,
  not only dependency updates). It compares the hashes of the three files with the manifest, as the check does;
  without a readable manifest there is no refusal.
- The check reports dangerous constructs in every generated `.rs` file and in `generated/rust/README.md` (its code
  blocks run as doctests), with a fixed prefix so the skill can stop before running `cargo`: `std` paths to `process`,
  `net`, `fs`, `os`, `env`; `std` followed by `as`, `::*` or `::{`; the words `extern` and `unsafe`; the macros
  `include!`, `include_bytes!`, `include_str!`, `env!`, `option_env!`; `path =` in an attribute; a root `build.rs` or a
  `build` key in `Cargo.toml`; a root `rust-toolchain` file, which rustup prefers over `rust-toolchain.toml`. A few
  plain regular expressions over the full text, comments included. Today's uses are allowed by an exact line per file
  in the script, not by markers in the generated code, which the generator could write itself.
- The checks catch accidents, not deliberate hiding; the review stays.
- Two merge requests: the Cargo refusal first, then the dangerous constructs.

## Consequences

**Positive:** A regeneration cannot silently change the Cargo files, and the most likely dangerous constructs are
reported before the skill builds or tests the code.

**Negative:** A Cargo change needs an extra step (`--update-dependencies` before `--update`). A new legitimate use of a
blocked construct needs an allowlist entry in the script. In a merge request the check only warns and runs next to
`rust_test`, so the CI may build code with a reported construct before anyone reads the warning.

## Out of scope & deferred

- A report of test names added or removed in Python without a matching Rust test (user decision: deferred; `--diff`
  already shows added and removed `def test_` lines, and the skill tells the generator to check them).
- Making `rust_test` wait for the dangerous-construct check, together with a CI job without network access.
- A `generated/.cargo/` folder above the crate, which Cargo also reads and the check does not reject yet; likewise a
  `Cargo.toml` with a `[workspace]` above the crate, which Cargo looks for because the crate has no `[workspace]`.

## Alternatives rejected

- cargo-geiger or cargo-deny: new tools for what a few regular expressions catch.
- Parsing the Rust code (e.g. with `syn`): needs Rust tooling in the check.
- Allow markers in the generated code: the generator could add them itself.
- Running the whole check in `--update` and refusing on its reports of Cargo files: it would also refuse on other
  problems of these files, which `--update` reports itself.
- A test-name check in the CI: the table in `generated/rust/README.md` that maps the tests is prose, and many Python
  tests are deliberately not ported.

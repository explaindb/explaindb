# 024 — Skill /regenerate-rust
**Date:** 2026-10
**MR:** https://gitlab.cs.uni-saarland.de/bigdata/dbsys/explaindb/-/merge_requests/170
---
## Context

The Rust code in `generated/rust/` is generated by an AI from the Python code in `system/`. A first skill that
described the regeneration in prose (closed MR !163, about 360 lines) kept breaking: every review round found a new
special case of git, hash or rebase handling. The mechanical steps are now tested tools in `.ci/check_generated.py`
(021–023): the check (out-of-date and hand-edited files, missing copies, dangerous constructs), `--diff` (the change
of each Python source since its Rust files were generated), `--update` (records the hashes and copies, refuses changed
Cargo files) and `--update-dependencies`. The translation rules are the tables in `generated/rust/README.md` and the
section "Rust code" of `CONTRIBUTING.md`. What is left for a skill is judgment: classify a change and translate it.

## Decision

- A short project skill `.claude/commands/regenerate-rust.md` (about 50–60 lines); it calls the tools and links the
  rules instead of repeating them, and holds only judgment and stops. The stop rules stand once, at the top.
- Two modes: keep the port up to date (from the check's out-of-date files, on `chore/regenerate-rust-<topic>`), or,
  after a clean check, port a new part the user names (user decision) through `/design` and `/develop`.
- A design decision at any step stops the run before `--update` and leads to `/design`, as `--update` records every
  Rust file as current. A Cargo change or a new allowed line of the dangerous-construct check needs the design and,
  again, the user's yes (user decision). Other unexpected reports stop the run.
- The skill does not track which files it changed: during a run, out-of-date, new and hand-edited files are
  expected. The review checks the classification instead: it gets the kept `--diff` output (or the design) and
  compares every Python change with the Rust code, also where nothing was ported.
- The check compares allowed lines without whitespace on both sides, so a line can be added as the check shows it.
- A repository test checks that every option the skill writes after `.ci/check_generated.py` exists, so a renamed
  option cannot break the skill unnoticed; the CI runs it also when a merge request changes only the skill.

## Consequences

**Positive:** The skill stays short; the steps that broke the first skill are tested code. A regeneration stops at
every point where a person has to decide (design, Cargo, dangerous constructs).

**Negative:** The prose of the skill itself is not tested beyond the option names. Porting a new part needs a clean
check first, so an out-of-date port is brought up to date in its own merge request beforehand.

## Out of scope & deferred

- A report of test names added or removed in Python without a matching Rust test (deferred in 023).
- Tests of the skill's behaviour beyond the option names.

## Alternatives rejected

- A long skill with git and hash procedures: rejected with !163; such steps belong in tested tools.
- A regeneration that runs automatically in the CI: the AI's output needs a person's review.
- Porting a new part entirely inside the skill: rules for folders, `mod` lines and test programs would make it long;
  `/design` and `/develop` already cover a new feature, and the check reports missing test programs.
- A separate agent for the comparison of Python and Rust: the code reviewer of `/finish-feature`, told to compare,
  suffices.
